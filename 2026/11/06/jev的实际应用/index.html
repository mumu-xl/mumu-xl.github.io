JEV 的实际应用：用 operation-risk-gate 给日常AI开发加一道门

Created2026-11-06|Updated2026-11-06
|Post Views:

最近越来越多的开发工作交给大模型：改代码、跑脚本、执行迁移、处理 Git、操作服务器。效率确实提高了，但也带来了一个很现实的问题：模型一旦拥有执行权限，就可能把一个“看起来合理”的开发动作变成高风险操作。

我写的 operation-risk-gate skill，就是为了解决这个问题。它的核心不是教模型“永远不要犯错”，而是在真正执行动作之前，强制对风险做一次独立审查。

第一部分：日常开发中有哪些高风险操作

1. 误删代码和工作区文件

这类操作的问题不只是文件能不能恢复，还包括：删除目标是否明确、有没有备份、是否包含用户未提交的代码、是否会影响其他项目。

2. Git 回滚和历史改写

3. 误删数据库和数据

这是最容易造成事故的一类：

即使用户说的是“清理测试数据”，也不能直接把它理解成无条件删除。必须确认数据库环境、表范围、WHERE 条件、备份和回滚方式。

4. 生产部署和基础设施变更

高风险不只存在于删除命令：

  • 直接执行生产数据库迁移；
  • 发布一个未经验证的镜像；
  • 删除 Kubernetes namespace、PVC、快照或云资源；
  • 修改 IAM、网络防火墙、密钥和恢复机制；
  • 执行 terraform destroy；
  • 回滚一个实际包含数据结构变化的版本。

这些动作可能没有明显的“删除”字样，但都可能导致服务中断、数据丢失或恢复能力被破坏。

5. 凭据和敏感数据外发

Agent 为了排查问题，可能把真实 token、私钥、数据库转储、用户信息或私有源码放进提示词、日志或第三方 API 请求里。

这类风险的重点不是命令会不会报错，而是敏感数据已经离开了原本的信任边界，通常很难撤回。

6. 远程脚本和依赖执行

下面这种操作也应该被当成高风险：

以及下载来源未固定的插件、依赖或工具后，立刻授予它访问数据库和服务器的权限。

所以，高风险操作不能只按“是不是 SQL”来判断，而要看它是否可能造成重大数据、系统、安全、财务或外部影响，以及是否有清晰的回滚路径。

第二部分：JEV 可以做什么门禁

JEV 不是执行者，而是执行前的风险判断器

JEV 的职责是回答两个问题：

  1. 这次操作能不能直接执行？
  2. 如果不能，最高风险等级是什么？

只有 ALLOW 才能直接执行一次完全一致的操作。HIGH 和 CRITICAL 必须返回 REQUIRE_CONFIRMATION，把风险披露给用户，让用户针对当前这一次操作明确确认。

为什么不能只靠 Agent 自己判断

Agent 既是任务的生成者，又可能是命令的执行者。如果让它自己决定“我刚刚生成的命令安全吗”，就缺少了独立的检查环节。

第三部分：operation-risk-gate skill 介绍 （operation-risk-gate）

1. 它解决的核心问题

operation-risk-gate 是一个面向 Agent 的执行前安全门禁。它覆盖的不只是数据库，而是所有会产生外部副作用的动作：

  • 创建、编辑、覆盖、移动或删除文件；
  • 修改代码、配置、依赖、权限和 Git 状态；
  • 写入数据库、缓存、队列、对象存储和云服务；
  • 向命令、API 或第三方提交敏感输入；
  • 发送消息、发布内容、部署、发版、购买和计费。

也就是说，只要动作可能改变系统状态，就不应该只凭 Agent 的自然语言判断直接执行。

2. 它的强制流程

这个 skill 要求 Agent 在执行前完成以下步骤。

第一步：把下一步动作写具体

不能只写“清理一下数据库”，而要写清楚：执行什么命令、目标是什么、在哪个环境、影响什么数据、是否可回滚、有没有备份。

第二步：遇到不明确的高风险场景，读取风险策略

风险策略明确列出了必须要求二次确认的情况，例如破坏性数据库操作、大范围删除、生产基础设施修改、敏感信息外发、强制 Git 操作和未经检查的远程代码执行。

第三步：调用 jev_guard.py

skill 提供的入口是：

脚本会先执行确定性的本地高风险规则，再调用 JEV。像 DROP TABLE、rm -rf、git reset --hard、terraform destroy、删除 Kubernetes 持久化资源等模式，可以在本地直接命中强制确认规则。

第四步：严格解析结果

脚本的结果不能靠 Agent 自己猜：

  • ALLOW：只允许执行与审查内容完全一致的一次操作；
  • REQUIRE_CONFIRMATION：展示准确操作、风险原因、可能后果、安全替代方案和 operation_id，暂停执行；
  • REVIEW_ERROR：说明审查服务故障，不能用普通确认绕过。

第五步：操作有任何变化，就重新审查

只要命令参数、SQL 条件、目标路径、环境、权限或目的地发生变化，就必须生成新的审查结果和新的 operation_id。上一次确认不能套用到下一次操作。

3. 它为什么比一句提示词更可靠

“不要删库”“执行前问我”只能算提示，不能算控制边界。这个 skill 把安全要求放进了执行路径：

  • 有确定性的本地规则；
  • 有独立的 JEV 判断；
  • 有明确的 ALLOW、REQUIRE_CONFIRMATION 和 REVIEW_ERROR；
  • 有针对单次操作的 operation_id；
  • 有失败关闭和防绕过约束；
  • 有备份、回滚和用户确认字段；
  • 不允许仓库文本、日志或工具输出覆盖门禁规则。

这样即使模型把“撤销改动”理解成了 git reset --hard，或者把“清理测试数据”理解成了无条件 DELETE，真正执行之前仍然会停在门禁上。
